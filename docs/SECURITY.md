# نموذج الأمان

## حدود الثقة

المتصفح غير موثوق. يستخرج الخادم الهوية من رمز جلسة عشوائي، يبحث عن بصمته في PostgreSQL، ثم يضع `user_id` و`role` في معاملة قاعدة البيانات. تستخدم سياسات RLS هذه القيم لتقييد الصفوف حتى لو نسي استعلام في المستودع شرط التصفية.

حساب `masar_owner` مخصص للترحيلات فقط، بينما يتصل التطبيق بحساب `masar_api` محدود الصلاحيات. لا تستخدم حساب المالك في تشغيل API.

## قرارات رئيسية

- لا JWT في المتصفح: الجلسات الخادمية أسهل في الإبطال الفوري والتحكم المركزي.
- لا أسرار في تخزين الويب: Cookie الجلسة `HttpOnly`.
- لا تشغيل لكود الطلاب داخل عملية API ولا وصول لها إلى Docker: يرسل API عقدًا موقّعًا بسر داخلي إلى Runner مستقل، ثم ينفذ Runner حاوية مؤقتة بلا أسرار، وبشبكة مغلقة وحدود CPU/ذاكرة/عمليات/وقت ونظام ملفات للقراءة فقط.
- الاستجابة لدخول فاشل موحدة لتقليل كشف وجود الحسابات، مع تنفيذ تحقق وهمي لكلمة المرور عند غياب الحساب.
- البريد ورقم الجوال مقيدان بالتفرّد في قاعدة البيانات؛ ويُوحّد الجوال إلى E.164 قبل التخزين والبحث لمنع تكرار الهوية بصيغ مختلفة.
- حساب الطالب لا يُحفظ دون مستوى أكاديمي، وتتحقق قاعدة البيانات من نشاط المستوى والتخصص والدائرة قبل الإنشاء أو التعديل، بينما تُزال هذه العلاقة تلقائيًا عند تغيير الدور إلى أستاذ أو مدير.
- تغيير دور المستخدم أو إيقافه يبطل جلساته الحالية، ولا يستطيع المدير تغيير دوره أو حالته من جلسته الحالية، كما تمنع قاعدة البيانات إزالة آخر مدير نشط.
- إنشاء المقررات محصور بالمدير في الواجهة وAPI وسياسة RLS، ولا تقبل قاعدة البيانات مالكًا للمقرر إلا إذا كان حساب أستاذ نشطًا.
- كل مقرر مرتبط بمستوى عبر مفتاح أجنبي غير قابل للفراغ، وتتحقق قاعدة البيانات من أن المستوى والتخصص والدائرة كلها نشطة قبل الإنشاء.
- إضافة الدوائر والتخصصات والمستويات محصورة بالمدير، وتنفذ عبر دوال `security definer` تتحقق من حساب المدير النشط وتسجل كل عملية في سجل التدقيق.
- تعديل الهيكل الأكاديمي يتطلب تطابق هوية المدير في الجلسة مع هوية المنفذ داخل قاعدة البيانات، ويُحفظ القيم السابقة والجديدة في سجل التدقيق.
- تعديل المقرر أو حالته محصور بالمدير مع تحقق مزدوج في API وقاعدة البيانات، وتُحجب المقررات الموقوفة عن الأساتذة والطلاب مع إبقائها مرئية للمدير.
- أحداث الأمان الأساسية مدققة، وعناوين IP تُسجل كبصمة HMAC لا كنص صريح.
- سياسات RLS تفصل التدريبات والمحاولات والنقاط حسب عضوية المقرر؛ ولا يقرأ الطالب الاختبارات المخفية أو الحل المرجعي، وتفرض قاعدة البيانات منح النقاط مرة واحدة فقط.
- تفصل قاعدة البيانات تعريف المقرر عن طرحه الفعلي في فصل وشعبة، وتطبق RLS على الطرح وعضوياته. رُبطت السجلات القديمة بطرح نظامي انتقالي لتفادي اختلاط الدفعات عند التوسع.
- لكل تدريب وواجب سجل نشاط تعليمي عام خاضع لـRLS، بينما تبقى التفاصيل الحساسة في جدول النوع المتخصص.
- مدققات مخرجات التدريبات محددة مسبقًا داخل المنصة، ولا يُنفذ كود تحقق يقدمه الأستاذ. وتعمل حلول الطلاب داخل حاوية معزولة بلا شبكة وبصلاحيات وموارد محدودة.
- تعديل التدريب المنشور ينشئ إصدارًا جديدًا لحالات الاختبار دون حذف نتائج الإصدارات السابقة، ولا يسمح بنقله إلى مقرر آخر حفاظًا على عزل الطلاب والمحاولات.
- عرض شفرة محاولة الطالب محصور بالمدير وأستاذ المقرر، ولا يعيد البريد أو رقم الجوال في شاشة المتابعة، كما يسجل كل فتح للشفرة في سجل التدقيق.

## متطلبات الإنتاج

- HTTPS إجباري مع HSTS، واتصال TLS موثق إلى PostgreSQL.
- أسرار مستقلة بطول عالٍ من مدير أسرار مع تدوير دوري.
- نسخ احتياطي مشفر، واختبار استعادته، ومراقبة محاولات الدخول والأقفال والأخطاء.
- تقييد CORS إلى أصل الواجهة الفعلي، وعدم استخدام wildcard مع credentials.
- تشغيل API وقاعدة البيانات بحسابات نظام غير مميزة، وتحديث الاعتماديات دوريًا.
- تشغيل عمال التنفيذ على مضيفين مخصصين؛ وعدم تعريض Docker socket العام لحاوية API في الإنتاج.
- إضافة MFA للمديرين قبل الاستخدام المؤسسي، وسياسة استعادة كلمة مرور مرتبطة ببريد موثوق ورموز أحادية قصيرة العمر.

## ما لا تدعيه هذه النسخة

هذه قاعدة قوية لنسخة أولية وليست اعتمادًا أمنيًا نهائيًا. قبل استقبال بيانات حقيقية يلزم فحص اختراق، مراجعة إعداد البنية التحتية، إدارة مفاتيح احترافية، وسياسات خصوصية واحتفاظ بالبيانات.
